# AXF-129 — Pagamento por terceiro sem reembolso automático

- **Jira:** https://axon-personal-finances.atlassian.net/browse/AXF-129 (parent AXF-1; split from AXF-5)
- **Branch:** `feature/AXF-129-no-automatic-debt` (base `origin/sprint/sprint-4` @ `337394d`).
- **Siblings already delivered and extended, not rebuilt:** AXF-126 (`propose`/`confirm`/`discard`,
  guard, integrity reads, controller), AXF-127 (derived singular projection) and AXF-128
  (neutralization of the counter-entries in the consolidated view, `reverse.v1`).

> Two rules only: (1) confirming the economic allocation of a third-party payment must not generate
> debt — no question, no debtor/creditor review, no reimbursement obligation, no balance, no partial
> settlement, no due date; (2) a transfer between accounts stays two distinct movements and is never
> renamed into one allocation or one refund, and it duplicates no revenue/expense in the
> consolidated totals. No new object, field, permission set, Custom Label or metadata container.
>
> **Diff of this pass: one test class (and its unchanged `-meta.xml`) plus this document. No
> production class changes at all — the guard rule the previous pass had added is gone, so
> `ALT_CLS_EconomicAllocationGuard.cls` is back to its base content.**

## AC-1 → implementation

**The confirmation writes nothing but the set and its parcels.** `confirm()` moves the set to
`CONFIRMED`, stamps `EffectiveAt`, takes the single active token and derives the singular projection;
the parcels are written by `propose()` and never edited. There is no counter-entry record, no
obligation record and no review item anywhere in that path — FR-50's counter-entries exist only
inside a consolidation calculation, as in-memory `Contribution` values keyed by account, currency and
source. A derived value cannot become a debt because nothing persists it.

**Absence is asserted against the ratified vocabulary, not against intuition.** The test enumerates
the custom fields of `EAS` and `EA`, the restricted values of `AXF_RVI_PKL_Type__c` and the accepted
types of `ALT_CLS_ReviewQueueService`, and fails if any of them names a debt, an obligation, a
debtor/creditor review, a balance, a partial settlement or a due date. Positive controls (the
aggregate really has custom fields; the queue really has types; the view really has members) keep
the absence claims from being vacuous.

**F2 — the list was missing the AC's own word, and now carries it.** The closed list is
`DEBT/DEBTS/DIVIDA/DIVIDAS`, `OBLIGATION/OBLIGATIONS/OBRIGACAO/OBRIGACOES`,
`REIMBURSEMENT/REIMBURSEMENTS/REIMBURSE/REEMBOLSO/REEMBOLSOS`, `DEBTOR/DEBTORS/DEVEDOR/DEVEDORES`,
`CREDITOR/CREDITORS/CREDOR/CREDORES`, `OWED/OWES`, `REFUND/REFUNDS/ESTORNO/ESTORNOS`,
`DUE/DUEDATE/VENCIMENTO/VENCIMENTOS`, `BALANCE/BALANCES/SALDO/SALDOS`,
`SETTLE/SETTLED/SETTLEMENT/SETTLEMENTS/QUITACAO/QUITACOES`,
`INSTALLMENT/INSTALLMENTS/PARCELAMENTO/PARCELAMENTOS`, `REPAY/REPAYMENT`,
`LIABILITY/LIABILITIES/PASSIVO/PASSIVOS`, `RECEIVABLE/RECEIVABLES/PAYABLE/PAYABLES`. Before this
pass **OBLIGATION/OBRIGACAO, DEVEDOR and CREDOR were absent**, so a field or review type literally
named for an obligation — the word the AC itself uses — would have passed the "no obligation" proof.

**F3 — the match is now by token, never by substring.** A name is split on non-alphanumeric
separators and on camelCase transitions (`AXF_EAS_DAT_DueDate__c` → `AXF`, `EAS`, `DAT`, `DUE`,
`DATE`; `TRANSFER_SUGGESTION` → `TRANSFER`, `SUGGESTION`) and each token is compared for equality
with the concept. `DUE` no longer matches `RESIDUE` or `OVERDUE`; `OWED` no longer matches `ALLOWED`,
`DISALLOWED` or `ENDOWED`; a legitimate `TRANSFER_SUGGESTION` question type or `AXF_EAS_EXI_SetKey__c`
field is accepted. `theDebtVocabularyJudgesTokensAndNotSubstrings` is the control for that: it asserts
the matcher still catches debt-shaped names **and** that it does not accuse those unrelated ones, so
reverting to substring matching fails a test instead of blocking a future delivery. The assertion is
scoped to the three surfaces named above — it is a vocabulary fence over the allocation aggregate and
the review queue, not a repository-wide naming law.

**F4 — the read-surface assertion no longer pretends to be §5.** The constant is renamed
`IMPLEMENTED_SET_VIEW_MEMBERS` / `IMPLEMENTED_SHARE_VIEW_MEMBERS` and the equality is described as
what it is: the members **this projection implements**. §5 ratifies more on the aggregate — set key,
active token, attributed-account projection, operation keys, plus the parcel's parent set and
redaction policy — and none of that is projected here. Rather than silently freezing that gap as
"the contract", `SET_MEMBERS_NOT_PROJECTED` and `SHARE_MEMBERS_NOT_PROJECTED` name those members and
the test asserts, one by one, that the view does **not** expose them. A §5 amendment that adds a
legitimate member now has to touch an explicit list instead of tripping over an equality that was
really about a projection.

**F1 — the guard rule was removed (option b), and the declared field is not the fence.** The
previous pass added two rules to `ALT_CLS_EconomicAllocationGuard`: a set must be born with a
positive `AXF_EAS_NUM_FactMagnitude__c`, and no parcel may exceed that field. Both were removed and
`ALT_CLS_EconomicAllocationGuard.cls` is now byte-identical to `origin/sprint/sprint-4` — the file is
no longer part of the diff. Why (b) and not (a):

- **The premise was unsound.** `AXF_EAS_NUM_FactMagnitude__c` is a value the writer itself supplies
  on insert and the guard never compared it with the anchored fact's real magnitude, so a writer
  inside the write window could declare an arbitrary magnitude and clear any parcel ceiling. A rule
  whose premise a writer controls proves nothing about what the aggregate then expresses. Making it
  sound means reading BAT/CCT/FTX inside the allocation trigger (up to three extra queries per DML)
  and deriving the movement per anchored fact.
- **It had no aggregate check, and adding one is not cheap or clean.** Making it complete means
  querying the sibling parcels of each set on every allocation DML and validating the sum of
  magnitudes _and_ of percentages per set, correcting for the old values of updated rows. And the
  percentage sum cannot be a fence anyway: `propose()` legitimately accepts a DRAFT whose shares
  total **less** than 100 (`total > 100` is the only total rejection), so an aggregate-percentage
  rule either forbids a legitimate partial draft or does nothing about the "partial residual" shape a
  reviewer flagged. That is machinery for a fence that is not a fence.
- **No reachable caller can violate it.** `propose()` rejects a non-positive percentage and derives
  each magnitude from `fact.magnitude × percent / 100` with `percent ≤ 100` and the residue going to
  the largest share; `reverse()` writes exactly the fact magnitude at 100%; `confirm()` requires
  exactly 100% and `MAGNITUDE_NOT_CONSERVED`. The stories' own review argument was therefore right:
  the rule was speculative, it only fired inside a write window no legitimate caller opens, and it
  still left the aggregate case open.
- **Removing it loses no proof, because the service's checks are what actually hold.** The four
  negative methods below now demonstrate, through the real paths, exactly the four shapes the guard
  was meant to fence — including the aggregate one it never checked.

**And the shape that could manufacture debt is refused — by the service.** The only way the aggregate
could express an amount someone owes is an amount that does not fit the movement it claims to share,
or a set claiming a movement that is not the anchored fact's. `confirm()` derives the movement from
the anchored BAT/CCT/FTX, refuses a declared magnitude that is not that movement's own
(`FACT_CHANGED`), refuses a parcel (or a sum of parcels) that does not conserve it
(`MAGNITUDE_NOT_CONSERVED`), and requires exactly 100%. The tests prove each of those refusals
independently and prove that the legitimate DRAFT still confirms afterwards.

## AC-2 → implementation

**Distinct movements.** The test builds a transfer as AXF-32 defines it: a `DEBIT` fact on the
origin's bank account and a `CREDIT` fact on the destination's, each with its own source key, its own
account and its own amount. Nothing links them — this story creates no `InternalTransfer` and no
neutrality key — and both stay visible in their own accounts.

**Not a renamed refund, and no duplicated revenue/expense.** Consolidating both holders returns
`inflow` 500, `outflow` 500, `net` 0 and `factCount` 2: each leg contributes exactly once, at its own
holder, and the pair is neutral, so the transfer duplicates nothing. The aggregate cannot become the
pair: `EAS` anchors to exactly one movement, which the test proves both positively (the allocation of
the paid leg anchors to that leg and to nothing else) and negatively (a set carrying two anchors is
refused by `EAS_VR_AnchorExclusive`).

**The distinction between the two cases.** A third-party payment is an _economic attribution of one
movement_: the destination assumes the leg it received, the consolidated view shows that leg as
`ALLOCATION` for the destination and the received leg as `HOLDER` for the same destination, the totals
stay at 500/500/0, and the other leg keeps its magnitude, its identity and no set of its own. The
difference in holders is expressed as a share — never as a receivable, a payable or an obligation.

**F5 — the distinction now runs through the real paths, and what stays outside is named.** The two
structural tests above are still structural: they build both legs with direct DML and assert
consolidation arithmetic, so on their own they would not have demonstrated that a transfer is never
_treated_ as a refund. This pass adds the two paths where that treatment could actually happen:

- `ALT_CLS_TransactionObservationService` — the real classification path. A `DEBIT` leg whose
  operation type is a transfer (`PIX`) leaves the observation as `EXCLUDED` with reason `TRANSFER`
  and provenance `OPERATION_TYPE`; a reversal-like leg (`ESTORNO`) leaves as `EXCLUDED` with reason
  `REVERSAL` and provenance `DESCRIPTION_RULE`. `ELIGIBLE` is 0 for both, so neither a transfer nor a
  refund can be promoted to a consumption expense or reach an allocation, and no set, parcel or
  question is created.
- `ALT_CLS_SourceLinkService` — the real routing path. A leg declared as `TRANSFER`, `REFUND` or
  `INVOICE_PAYMENT` is refused with `UNSUPPORTED_ECONOMIC_ROLE` **before any read of a candidate and
  before any write**, and the test asserts that no `AXF_OBJ_ReconciliationAllocation__c` row exists
  afterwards.

What this pass does **not** do, stated plainly: it does not implement routing for a transfer or a
refund role. That capability is AXF-135's and its absence is what produces the refusal. The transfer's
own netting (`AXF_ITR_EXI_NeutralityKey__c`) remains AXF-32's contract.

## Judgement calls and residuals

- **The deliverable was chosen from evidence.** Before writing anything the question was whether a
  debt concept exists to remove, or a missing guard exists to add. It does not exist to remove:
  §5's field list has no debt, obligation, balance, settlement or due-date field, no object in this
  branch carries one, and the counter-entries of FR-50 are never persisted. So the honest deliverable
  is contract-fixing assertions that pin the absence — the field, question and read-surface
  vocabulary checks — plus the four negative proofs of the shape that could manufacture an obligation
  from the aggregate, plus the AC-2 distinction. The one production rule the previous pass added was
  withdrawn (F1/b above) rather than replaced. No speculative machinery: no object, field, permission
  set, label, config flag or new class besides the test class.
- **`reverse()` is not exercised by this pass.** The tests call `propose()` and `confirm()`. The
  previous version of this note claimed the positive control re-proved both `propose()` and
  `reverse()`; no test in this class calls `reverse()`, so that claim is dropped rather than kept.
- **The XOR validation rule belongs to AXF-126 and was only asserted, never changed.** It is the
  structural reason an allocation can never embody a transfer pair, which is AC-2's own claim, so
  asserting it here is evidence rather than scope creep; the rule itself is untouched and had no test
  before this pass.
- **Nothing was absorbed from AXF-32 or AXF-41.** `AXF_OBJ_InternalTransfer__c` was not created, no
  neutrality key was introduced, no transfer detection or suggestion was added, and the card
  chargeback/credit/dispute slice (AXF-41) is untouched.
- **PENDENCY — the transfer's own neutralization is not implemented here, and must not be.** In a
  scope that holds only one side of a transfer, that side still contributes its own leg: the netting
  of the pair is AXF-32's contract (`AXF_ITR_EXI_NeutralityKey__c`), and AXF-32 is blocked by AXF-31
  and not in this branch. This pass proves only that the transfer is not _duplicated_ and not
  _renamed_ — the two claims AXF-129 owns.
- **PENDENCY — `AXF_OBJ_InternalTransfer__c` does not exist in this branch.** The AC states that
  AXF-32's contracts "remain intact", which was read as "do not touch or rename them", not "implement
  them". No test asserts the object's absence, because such a test would fail the day AXF-32 lands.
- **RESIDUAL — the vocabulary fence cannot see a field that does not exist yet.** The column is
  covered by the token assertion, which fails if a debt-shaped field, question type or view member is
  later introduced; a ratified §5 amendment that adds a legitimate member will have to update that
  list, which is the intended behaviour of a contract test.
