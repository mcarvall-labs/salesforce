# AXF-140 — Ties, uncertainty and partial / multi-currency candidates

Edge-case slice of AXF-29 under `AXF-MATCHING@1.0.0`, stacked on AXF-139
(`ALT_CLS_MatchEvidence`, `ALT_CLS_SourceLinkService`). It consumes the candidate presentation of the
sibling story; it does not rebuild it.

## Components

| Component                             | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ALT_CLS_MatchEvidence` (AXF-139)     | Declares the state vocabulary this workbench emits — `CONSULTATIVE`, `PARTIAL`, `BLOCKED` (policy §3/§5) — and carries withheld-evidence handling: a redacted identity carries no value and never satisfies `EXACT`, so it cannot order. Withholding is an authorization fact; absence is `UNKNOWN`.                                                                                                                                                                                                                                                                           |
| `ALT_CLS_SourceLinkService` (AXF-134) | Candidates in another currency are listed with their facts kept apart (`amount` original, `residual` available, `currencyIso`, `conversion`, `residualAfter`), stay `BLOCKED` and are never selectable; they are read in a scan window of their own so they cannot crowd out linkable candidates. A linkable candidate whose remainder stays non-zero is `PARTIAL`. The indicative quote is selected by the approved side, deterministically, and a newest non-positive rate leaves the pair unusable. Confirmation without material FX is refused with `MISSING_MATERIAL_FX`. |
| `aXF_LWC_sourceLink` (AXF-134)        | Renders the server state (every state the service emits, `PARTIAL` included), the server-provided reason beside the state badge, the conversion evidence line and the remaining residual. A blocked candidate shows no draft allocation action.                                                                                                                                                                                                                                                                                                                                |

## Rules

- **No tolerance, weight, default rate or conclusion policy is introduced.** Policy v1.0.0 approves
  none, so nothing here invents a number: a remainder of `0.01` is reported as `0.01`, and ordering
  stays the presentation order of AXF-139 (never a score).
- **Partial means explicit.** `residualAfter` is the remainder left on the candidate once the
  source's available amount is applied to it (same currency), computed as
  `available − min(source available, available)`. It is filled for persisted and virtual candidates
  alike, so a `null` has one meaning only — another currency, where the remainder is unknown and
  never zero — and the same cell always renders something.
- **`PARTIAL` is where the policy requires it (policy §3).** A linkable candidate left with a
  non-zero remainder is `PARTIAL`; a candidate the source extinguishes exactly stays `CONSULTATIVE`.
  A projected occurrence stays `CONSULTATIVE` as well: `PARTIAL`'s allowed actions (policy §5 — add
  or edit allocations, save draft) do not exist before the line is materialized
  (`MATERIALIZATION_REQUIRED`). The page keeps the consultative baseline; the state is per candidate.
- **Another currency is a blocked candidate, not a hidden one.** The candidate is shown — with the
  original amount, the original currency and the conversion evidence of the approved indicative
  layer (AXF-92 vocabulary `ESTIMATED` / `STALE` / `UNAVAILABLE`, its `QUOTE_MAX_AGE_DAYS` and
  `PROVIDER_BCB_PTAX` constants, one read per page) — because completion requires exact currency
  arithmetic (policy §3) and eligibility requires material FX evidence when currencies differ
  (policy §2). `linkable` stays false and the reason is named.
- **Blocked rows never crowd out linkable ones.** Same-currency and other-currency forecasts are read
  in two scan windows of `MAX_SCAN` rows each and then filtered by the same in-memory exclusion. A
  `BLOCKED` row can therefore no longer consume the window that decides which linkable forecasts are
  seen at all; a truncation in either window is still reported (`scanTruncated`, `maxScan` =
  `MAX_SCAN`, so the message stays true for both).
- **The rate is the approved side, chosen deterministically, and never a superseded fallback.** The
  quote is filtered by the side the approved FX layer derives for the same purpose
  (`ALT_CLS_RealizationService.recognize`: an outflow is converted at the `SELL` quote, an inflow at
  the `BUY` quote) and ordered by effective instant with record identity as the tie-break, so two
  competing quotes for one pair resolve the same way on every read. The `rate > 0` predicate is gone
  from the query: the newest row of the pair decides, and a non-positive newest rate leaves the pair
  `UNAVAILABLE` with no rate and no converted amount instead of silently presenting an older quote.
- **A missing material rate blocks confirmation.** `confirm` checks the material rate before the
  currency contract, so the refusal names what the user must correct (`MISSING_MATERIAL_FX`) when the
  pair has no usable quote; with a usable quote the refusal remains `CURRENCY_MISMATCH`. `AXF-25`
  still enforces exact currency, so a rate never turns a mismatch into an allocation.
- **Redaction is authorization; absence is `UNKNOWN`.** `externalIdentityRedacted` is set from the
  authorized-holder predicate on both sides, never from the presence of a key, so the external
  identity is a displayed evidence fact — the policy's first presentation criterion — and a side
  whose holder is not authorized is the one that withholds it. A side without an identity is absent:
  `UNKNOWN`, no values. The raw provider key still never travels as a field (`SourceView.sourceKey`
  stays transient). The genuinely withheld case is proven at the contract level in
  `ALT_CLS_MatchEvidenceTest.withheldIdentityIsRedactedAndCannotOrder`.
- **A blocked row states why.** Every server reason code travels with the candidate and is rendered
  beside its state badge through the same code → label map the failures use, so the user can see what
  to correct (`CURRENCY_MISMATCH`, `MISSING_MATERIAL_FX`, `MATERIALIZATION_REQUIRED`).
- **Virtual projection lines stay same-currency.** They are projections of the holder's own schedule
  and are never linkable before materialization (AXF-136), so no conversion evidence is derived for
  them.

## Judgement calls and limits

- "Unavailable evidence" is read as evidence this workbench does not disclose to the caller it is
  serving: an authorization fact. In this workbench the caller is authorized for the fact and for
  every candidate it is shown (`readSource` refuses an unauthorized holder), so nothing is withheld
  and the identity is disclosed as a fact. The earlier behaviour (`externalIdentityRedacted = sourceKey != null`)
  reported authorized evidence as withheld and turned absence into `REDACTED`; both are now wrong
  answers and are not produced. Ordering consequence: between a fact and a forecast the feature stays
  `UNKNOWN` — forecasts carry no external identity in v1 — so the first criterion is inert, not
  suppressed.
- A currency-differing candidate is shown but `BLOCKED` even when a usable quote exists, because
  `ALT_CLS_RealizationService` refuses an allocation whose source and target currencies differ
  (`CURRENCY_MISMATCH`, policy §3 "exact currency arithmetic"). It is therefore never linkable; the
  quote is presentation evidence for comparison, and the reason is named. Reconciling across
  currencies would need a new approved policy and a realization contract for it.
- The rate side is taken from the direction of the source fact rather than from a new matching
  input: that is the convention the approved conversion layer already uses for the same purpose, and
  inventing a per-candidate side would be a new policy.
- The indicative quote is read under sharing, not field-level security, exactly as the approved
  indicative layer does (AXF-92): the reference quote is shared data and its fields are not granted
  to every capability holder, so a field-level read would fail the whole workbench.
- No conclusion or completion state is persisted by this story. Recording the matching policy,
  cutoff, candidate identities and gate reasons on the confirmation belongs to AXF-30.

## Policy vs implementation — declared mismatch (not fixed in this pass)

1. `docs/policies/MATCHING-POLICY.md` in this branch is a mirror of the approved matching policy
   (Confluence page 6488065). The previous commit on this branch edited it, adding clauses 7–8 that
   describe this implementation. **This pass leaves the file untouched.** An implementation may not
   amend an approved policy mirror, so clauses 7–8 are unapproved text and must be withdrawn or
   approved by the policy owner; the authority remains the policy page and its snapshot
   (`_bmad-output/planning-artifacts/canonical-reconciliation-2026-08-27/snapshots/6488065.md`).
2. The approved text is itself in tension: §3 line 36 "All candidates remain `CONSULTATIVE` until the
   user constructs allocations" against line 40 "A non-zero residual remains `PARTIAL`". The
   implementation resolves it conservatively — `PARTIAL` only where a draft allocation can actually
   exist (a linkable candidate with a positive remainder), `CONSULTATIVE` for an exactly extinguished
   candidate and for projections that cannot be allocated before materialization — but that is a
   reading of the policy, not a policy decision. If the owner intends otherwise (no `PARTIAL` before
   an allocation exists, or `PARTIAL` for projections too), it is a policy change, not a code default.
3. `READY_FOR_CONFIRMATION` and `RESULT_UNKNOWN` (§5) are not emitted by this workbench: nothing here
   persists a conclusion or resolves an unknown command result. `READY_FOR_CONFIRMATION` belongs to
   the confirmation recording of AXF-30 and `RESULT_UNKNOWN` to the retry/authority path of AXF-25/
   AXF-137. The component maps every state this service emits; if a later change makes this service
   emit those two, `STATE_LABEL` and the labels must gain them in the same change, otherwise a raw
   server token would reach the user again.

## Declared pendencies

- **FX read posture (unchanged, for the user's decision).** Verified in `indicativeQuotes`: the
  exchange-rate read is a plain SOQL inside a `with sharing` class — record sharing enforced, object
  permissions and field-level security not — while every fact, candidate and allocation-verification
  read in the same service uses `AccessLevel.USER_MODE` / `WITH USER_MODE` (`bankSources`,
  `cardSources`, `readSource`, `persistedCandidates`, `virtualCandidates`, `netBySource`,
  `netByTarget`, `candidate`, `finish`), and the private `Conservation` counts stay system-mode by
  design (counts and booleans only, never amounts or rows). No access semantics were changed in this
  pass. Open for the user: whether the indicative quote may be read without FLS for capability
  holders, and whether the private verification counts should remain system-mode.
- **Golden fixtures GF-72–GF-75 are an open gap.** They are defined in the planning artifacts
  (`architecture-Axon-Finance-2026-08-21/GOLDEN-FIXTURES.md`, lines 90–93) and no equivalent fixture,
  test name or reference exists in this repository (`docs/` and `force-app/` searched). They were not
  invented here. Behavioural coverage today: GF-72 (consultative candidates, deterministic non-score
  ordering, policy version on every page) and GF-73's redaction clause are asserted by tests; GF-73's
  "exact external identity appears first" exists in `ALT_CLS_MatchEvidence.OrderKey` but is inert in
  this workbench because forecasts carry no external identity in v1; GF-74's `PARTIAL` is now emitted
  as a candidate-listing state, while GF-74's input describes the state after an allocation was
  constructed — that persisted draft state is not owned by this story; GF-75 (`RESULT_UNKNOWN`, retry
  blocked) has no implementation in this workbench at all.
- **UI verification is automated only.** The bundle was deployed to AXON_DEV and its behaviour is
  proven by the Jest assertions above; no manual walkthrough of the workbench was performed in this
  pass.
