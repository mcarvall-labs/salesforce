# AXF-134 — Link a bank/card source to a planned financial transaction (basic flow)

Basic link slice of AXF-28 under `AXF-SOURCE-LINK@1.0.0`. Realization is delegated to the AXF-25 contract (`ALT_CLS_RealizationService.apply`); this slice adds eligibility, candidate suggestion and explicit confirmation.

## Components

| Component                                                                  | Role                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ALT_CLS_SourceLinkService`                                                | `listSources(SourceQuery)` → eligible facts of one authorized holder; `readSource`; `listCandidates(CandidateQuery)` → persisted + virtual forecasts; `confirm(ConfirmInput)` → typed allocation through AXF-25, replay, CONFLICT. |
| `AXF_CLS_CTRL_SourceLink` + `aXF_LWC_sourceLink` + tab `AXF_CT_SourceLink` | Three-step wizard (source → forecast → review/confirm). Amount, currency and source stay visible; any change to the suggested amount or date needs an explicit review checkbox; one operation key per draft so a retry replays.    |
| `AXF_CanLinkSource`                                                        | Capability in `AXF_PS_GestorFinanceiro`; `AXF_CanRealize` (AXF-25, `AXF_PS_Realization`) is also required.                                                                                                                         |

## Rules

- **Eligible source** (revised contract 12/09/2026): an existing `AXF_OBJ_BankAccountTransaction__c` (BANK, Source ∈ PLUGGY/CSV/MANUAL — a published CSV is BANK with Source=CSV) or `AXF_OBJ_CreditCardTransaction__c` (CARD); status `POSTED`; parent bank account/card `AVAILABLE`; valid date/amount/currency/direction; holder in the authorized context list; no `OPEN` review item of any type on the fact (SOURCE_CHANGE / SOURCE_DELETE included, checked privately regardless of queue visibility); remaining amount > 0. Staging rows, CASH and null sources are never accepted (`INVALID_SOURCE`). Sources dated more than one year before today are not scanned. Eligibility is re-evaluated at confirmation.
- **Allocation verification**: the user-visible net per source/target is compared with a private allocation count; a mismatch marks the fact/forecast `ALLOCATIONS_UNVERIFIED` and withholds it (fail closed, no hidden amount leaves the boundary).
- **Candidates**: `AXF_OBJ_FinancialTransaction__c` with `PlanKind = PLANNED` of the same holder, currency and direction, `ScheduleState ≠ CANCELLED`, funding compatible (no funding, or the same bank account/card; a plan funded by the other kind is excluded), remaining amount > 0 (realized targets excluded after a `MAX_SCAN` = 200 row scan, flagged `scanTruncated` when more exist). Virtual occurrences of `ACTIVE` schedules (same holder/currency/direction, through `readProjection`) are shown for context as `linkable = false` / `MATERIALIZATION_REQUIRED` — materialization is AXF-136.
- **Ordering** is deterministic and score-free and, since AXF-139, follows the `AXF-MATCHING@1.0.0` presentation order (verified external identity, exact source identity, persisted before virtual, record identity). No amount or date tolerance is applied; manual search filters persisted forecasts by description with server-side pagination (`MAX_PAGE` = 50).
- **Suggestion**: amount = source remaining, capped by the forecast remaining; date = fact date. Nothing is linked automatically — a single candidate still needs explicit confirmation.
- **Confirmation**: source re-read and re-validated; `sourceVersion`/`targetVersion` must match (else `CONFLICT`); target validated (`INVALID_TARGET`, `TARGET_CANCELLED`, `TARGET_REALIZED`, `CURRENCY_MISMATCH`, `FUNDING_MISMATCH`, `ALREADY_LINKED`); amount/date different from the suggestion require `changesReviewed = true` (`REVIEW_REQUIRED`). Then `ALT_CLS_RealizationService.apply` creates the typed `AXF_OBJ_ReconciliationAllocation__c` (bank or card lookup) and, without a forecast, the `ACTUAL_ONLY` financial transaction born from the fact. The fact is never copied or altered; only its optimistic version moves. Any failure rolls back everything (AXF-25 savepoint) and the draft stays reviewable.
- **Idempotency**: the same operation key replays the previous allocation (`replayed = true`, even after the source became exhausted); a divergent payload under the same key answers `CONFLICT` (AXF-25 payload hash).
- **Errors** are sanitized `{code}` values; unauthorized and missing facts are indistinguishable (`UNAVAILABLE`).

## Validation

- AXON_DEV: `ALT_CLS_SourceLinkServiceTest` 6/6 (service 93 %, controller 88 %): eligibility exclusions (PENDING, CUSTODY parent, OPEN review, exhausted, one-year floor) with deterministic paging; candidate matching (holder/currency/direction/funding, cancelled/credit/USD/foreign/realized excluded, materialized schedule occurrences linkable, virtual lines non-linkable, manual search); confirm → typed bank allocation, fact content untouched, replay, CONFLICT on divergent payload / stale versions, `ALREADY_LINKED`, ACTUAL_ONLY without forecast, `INVALID_TARGET` for a realized-only plan; revalidation at confirmation with nothing persisted on failure; capability and foreign-holder fail-closed; controller strict JSON and sanitized codes.
- Jest 3/3; ESLint clean.
