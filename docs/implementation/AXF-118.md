# AXF-118 — Authorized data export with revalidated authorization

The export slice of AXF-9: request, generation, authorization and download. Closure orchestration
stays in AXF-119, the blocked/Pluggy states in AXF-120 and the restore invariant in AXF-121.

## Components

| Component                                   | Role                                                                                                                                                                                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `AXF_OBJ_ExportRun__c`                      | Private control record per (holder, requester): status, private artifact id, PII-free file name, SHA-256 content hash, short-lived window, safe reason, optimistic version. No Delete for business users.                      |
| `AXF_EPR_EXI_ScopeKey__c`                   | Unique = SHA-256 of holder + requester; one export per scope and author, replayed by the same key (NFR-3).                                                                                                                     |
| `ALT_CLS_ExportService`                     | Authorization, generation, two-stage revalidation, revocation. Every read **through the service** revalidates; the platform's own owner link is a declared residual (see "Residual limits"), not something this slice defeats. |
| `AXF_CanExportData`                         | Custom permission, granted by `AXF_PS_GestorFinanceiro`. Grants no Delete and no Files CRUD.                                                                                                                                   |
| `AXF_ExportReady`                           | In-app `CustomNotificationType` for the PII-free "ready" notice (D-80).                                                                                                                                                        |
| `ALT_CLS_CsvFormatParser.neutralizeFormula` | Promoted from private to `public`: AD-25 requires **one** active-content rule, so export and import now share it instead of keeping separate prefix lists.                                                                     |

## The export/download control, and what the ratified sources say

**They do not name one.** The requirement is ratified; the mechanism is not, and inventing one is
forbidden:

- `AXF-118.md:38` / `AXF-9.md:63` — "autorização é verificada na solicitação e novamente no download
  privado e de curta duração"; `AXF-9.md:135` — "Reauthorize the export request and each private,
  short-lived download… keep PII out of filenames, notifications and logs."
- `EXPERIENCE.md:236` — "Exportação verifica autorização também no download, expira, evita dados em
  nome de arquivo/notificação e registra escopo/ator."
- AD-21 (`ARCHITECTURE-SPINE.md:209`) — effective access governs "arquivo, export, e-mail e async",
  and G2/G5 converge "sem prometer apagar cópias externas já exportadas".
- `AXF-9.md:137` — "finalize the focused physical mapping before implementing that run";
  `AXF-9.md:107` — "Não inventar schema, operationId, provider, prazo, tolerância ou budget."
- `ContentDistribution` does not appear as an approved control anywhere in the ratified set; the one
  literal mention (`review-fx-current-fit.md:66`) is a recommendation to **prohibit** public
  links/ContentDistribution. It could not satisfy either criterion regardless: a public link carries
  no caller identity, so it cannot revalidate authorization on download.

**Control chosen (a declared judgement call):** a private `ContentVersion` whose
`ContentDocumentId` is held by the run, with **no `ContentDocumentLink` created by the service** and
**no `ContentDistribution` at all**; every read **through `ALT_CLS_ExportService`** revalidates
authorization and the stored hash. This is the "private, short-lived download" the story asks for,
implemented with the smallest native mechanism that can actually reauthorize.

What that control does **not** claim: that direct platform access is prevented. The platform attaches
its own link to the file when the `ContentVersion` is written, so the file is also reachable through
the Files surface by that owner without revalidation. The ratified FX resolution requires exactly
this caveat to be acknowledged and administered separately (`review-fx-current-fit.md:66`); the
guaranteed property is "all service reads revalidate", and the platform's own owner link is a
declared residual (see "Residual limits").

Two constraints found during implementation, both enforced by the platform:

- `ContentDocumentLink.Visibility = 'SharedUsers'` — the least-exposure record link — is
  **rejected** by the org (`INVALID_FIELD_FOR_INSERT_UPDATE`), leaving only `InternalUsers` /
  `AllUsers`, which would expose the artifact to the whole org. So the service creates no link.
- A custom lookup to `ContentDocument` is **not a valid `referenceTo`** in the Metadata API, so
  `AXF_EPR_TXT_ContentDocument__c` is a Text(18) field holding the document id.

## Acceptance criteria

1. **AC-1** — `request()` authorizes the caller (capability, holder visibility via `WITH USER_MODE`,
   read access through `UserRecordAccess`), then writes the artifact and its control row as one
   unit, and returns the PII-free file name, the content hash and the window. `download()`
   authorizes **again**: capability, the exact requester binding, holder access re-read from the
   platform, then the window; only then does it read the artifact and recheck its hash against the
   stored evidence. Cells are always quoted, embedded quotes are doubled and formula prefixes are
   neutralized (AD-25), so the export stays inert outside the org.
2. **AC-2** — **every** refusal that finds a live artifact revokes it: an elapsed window, a
   withdrawn capability, a lost requester binding (including a nulled one — the lookup is
   `deleteConstraint SetNull`), a withdrawn holder authorization, and an artifact that is missing
   or does not match its hash. The artifact document is deleted, its id, name, hash and window are
   cleared, status becomes `REVOKED` with a safe reason code, and no content is returned. A refusal
   that must commit a revocation is returned as a `DownloadView.outcome` and never thrown, because
   an unhandled exception would roll the revocation back. `read()` never revokes; it reports
   availability from the same gates `download()` applies — including the holder access re-read from
   the platform — so it never advertises a download that the next `download()` would refuse.
3. **NFR-18 (optimistic precondition)** — `request(accountId, expectedVersion)` and
   `download(runId, expectedVersion)` take the version the caller last observed
   (`RunView.version`), following the merged `ALT_CLS_ClosureOrchestrator.load(runId,
expectedVersion)`: an unstated or stale version is refused with a safe code (`INVALID_INPUT` /
   `CONFLICT`) before anything is written.

## PII discipline

- File name: `axon-export-<EPR-nnnnnn>.csv` — the opaque auto-number only. No holder name, no date,
  no fact description.
- Notification: fixed PT-BR text; the body names the artifact by its opaque number, the title names
  nothing. Asserted on the exact builder the service sends.
- Logs: one builder, one debug call site, carrying a fixed code plus the opaque number. No
  description, identifier or record value, and no address.
- The export CSV legitimately contains the holder's in-scope facts; nothing out of scope does.

## Assumptions declared (no ratified source fixes these — see "Decisions for the product owner")

- **Download window: 15 minutes** (`DOWNLOAD_WINDOW_MINUTES`). AXF-9:107 forbids inventing a
  deadline and the closed G7-3 retention table (`ARCHITECTURE-SPINE.md:669-676`) has **no export
  domain**, so this is a declared default, not a derived value. No `AXF_CMT_RetentionPolicy` record
  is shipped: AXF-101 requires the type to carry no shipped policy, and day-granularity eligibility
  could not express a short-lived download anyway.
- **Export scope: the holder's `FinancialTransaction` facts**, bounded by `EXPORT_ROW_LIMIT`
  (5000). Above the limit the request blocks with `EXPORT_TOO_LARGE` rather than truncating
  silently (NFR-19); paginating the artifact is a follow-up. Bank and card facts are not included
  yet.
- **Revocation is lazy.** There is no scheduler, so an expired artifact that nobody touches is
  removed at the next access. This matches the accepted pattern already recorded for AXF-119
  (`deferred-work.md:144`).
- **Notification text is hardcoded accent-free PT-BR**, following the merged Apex precedent
  (`ALT_CLS_SharedExpenseService`); D-86 custom-label i18n is implemented at the LWC layer in this
  repo, and no Apex class uses `System.Label`.

## Control plane: the fields that carry the control are read-only

The control that decides an authorization must not be editable by the party it authorizes. In
`AXF_PS_GestorFinanceiro` every non-required field of `AXF_OBJ_ExportRun__c` is now **read-only**
(`editable=false`) — the window, the artifact pointer, the hash, the file name, the reason, the
version and the requester binding — and the object grant no longer carries `allowEdit`. The service
performs every run transition in system mode after the caller was authorized by explicit checks, so
the state machine does not need that grant.

`grantRequesterAccess` writes a **`Read`** share. Read level is sufficient because the object-level
edit grant is gone: with no object-level Edit, no user can edit a run whatever the share says.

Required fields (`AXF_EPR_LKP_Account__c`, `AXF_EPR_EXI_ScopeKey__c`, `AXF_EPR_PKL_Status__c`) stay
**outside** the permission set, following the convention `AXF_OBJ_ClosureRun__c` already uses — and
here the platform enforces it: a permission set cannot carry a field entry for a required field.
Both attempts to give the scope binding explicit field-level security were rejected by `AXON_DEV`
with `You cannot deploy to a required field: AXF_OBJ_ExportRun__c.AXF_EPR_EXI_ScopeKey__c` and, for
the holder lookup, `…AXF_EPR_LKP_Account__c`. The read-only guarantee for those two fields is
therefore carried by the removed object-level edit grant and the `Read` share, not by field-level
security, and that is recorded here instead of assumed.

Verified by re-reading `AXON_DEV` after the deploy: `FieldPermissions` for
`AXF_PS_GestorFinanceiro` / `AXF_OBJ_ExportRun__c` return `PermissionsRead=true,
PermissionsEdit=false` for the seven fields above, with no rows for the required ones;
`ObjectPermissions` return `PermissionsEdit=false`, `PermissionsCreate=true`,
`PermissionsDelete=false`, `PermissionsModifyAllRecords=false`.

Because no user may edit a run, the service owns the whole state transition, and it now runs
`without sharing` — the same elevation the merged `ALT_CLS_SharedExpenseService` declares. A
`with sharing` write is refused for a requester who holds a read-only share, which is exactly the
caller this state machine serves, and the refusal paths must reach the run even after the caller
lost object access entirely. The elevation decides nothing on its own: every read that must respect
the caller's access states `WITH USER_MODE` explicitly (the holder lookup and the gated run reads),
the fact queries that build the CSV run in `USER_MODE`, and the capability, requester binding,
holder access and window are revalidated before any effect. The empirical note behind the change:
`AccessLevel.SYSTEM_MODE` does **not** bypass sharing rules inside a `with sharing` class — the
first test run failed with `INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY` on the run update and
`NOT_ACCESSIBLE` on the privileged read for a caller without a share.

## Residual limits (stated, not hidden)

- Revocation deletes the copy this application controls. A download already delivered cannot be
  recalled — AD-21 declares that an accepted limit.
- The platform adds its own `ContentDocumentLink` (`ShareType I`, the creating user) when the
  `ContentVersion` is written, and Files ownership always allows that user to open the file. That
  user is the authorized requester, so no third party gains access, but the artifact is reachable
  outside the service by its own requester. This is the platform-bypass caveat the ratified FX
  review says must be "acknowledged/administered separately" (`review-fx-current-fit.md:66`). The
  service therefore claims only that its own reads revalidate; it does not claim to prevent direct
  platform access, and it does not try to.
- A refusal that must commit a revocation is returned as a `DownloadView.outcome`, not thrown: an
  unhandled Apex exception rolls the transaction back, which would undo the revocation it is meant
  to record. This now covers **every** refusal over a live artifact (`EXPIRED`,
  `ACCESS_REVOKED` — also for a withdrawn capability or a lost requester binding, `FORBIDDEN`
  reported as the outcome — `ARTIFACT_MISSING`, `ARTIFACT_MISMATCH`, `ARTIFACT_NOT_REMOVED`).
  Failures with no side effect to preserve (`INVALID_INPUT`, `CONFLICT`, `NOT_ACCESSIBLE`,
  `EXPORT_TOO_LARGE`) are still thrown.
- **`ARTIFACT_NOT_REMOVED` is a recorded state, not an exception.** If the platform refuses to
  delete the document, throwing would roll the whole transaction back and leave the artifact alive
  with no record: the run is instead committed as `REVOKED` with the reason
  `ARTIFACT_NOT_REMOVED`, the document pointer is kept, and the next `download()`/`request()`
  retries the removal. An operator can therefore always see that a copy survived.
- **A refusal revokes for every caller, including one unrelated to the run.** That is what AC-2
  asks for, and it means an unauthorized caller who obtains a run id can destroy that artifact
  (a denial of service) — never obtain it. Run ids are opaque auto-numbers and are not enumerated
  anywhere; the trade-off is recorded here rather than silently preferred.

## Decisions for the product owner (not implemented in this pass)

These are requirements decisions, deliberately **not** taken here:

1. **No reachable entry point.** The slice ships a service with no `AXF_CLS_CTRL_*` controller and
   no `aXF_LWC_*` component, which is the house pattern for a user-facing capability. There is
   therefore no UI/API surface from which a requester can actually request or download. Whether this
   slice needs one — and with it the authorization, governor-limit and translation work that a
   controller implies — is a scope decision, and it is the most prominent open item of this story.
2. **The physical form of the new object was never ratified.** The audit confirmed the _need_, but
   `AXF_OBJ_ExportRun__c` (its fields, the `Text(18)` artifact pointer and the `EPR` acronym) does
   not appear in a ratified schema dictionary, and `EPR` is absent from the closed acronym table,
   whose own rule is to stop and ask for the naming standard. Neither the shape nor the name is
   changed here.
3. **The 15-minute window is an assumption to ratify.** G7-3 makes retention domain policy in
   `AXF_CMT_RetentionPolicy` ("UI, service and jobs use the SAME policy"), and the service currently
   hardcodes `DOWNLOAD_WINDOW_MINUTES = 15`. The constant is recorded here as a decision to ratify
   (with the policy source and the short-lived-download granularity question), not silently changed.
4. **Export scope and row limit.** The scope exports `FinancialTransaction` facts only, and AXF-106
   requires bank and card facts in the export; above `EXPORT_ROW_LIMIT` the request blocks instead
   of splitting resumable work (NFR-19). Both are requirement decisions.
5. **`evidenceRef` validation stays with AXF-119.** The handoff of the artifact reference to
   `ALT_CLS_ClosureOrchestrator` is unchanged and `ALT_CLS_ClosureOrchestrator` is untouched by
   this pass.

## Integration with the closure sibling

`RunView.evidenceRef` exposes the readable `ContentDocumentId` that AXF-119's `attachExportEvidence`
expects (its field description names that id and its code review deferred this validation to the
export story, `deferred-work.md:146`). AXF-118 does not modify AXF-119.
