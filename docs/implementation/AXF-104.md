# AXF-104 — coverage of the evidence write-boundary guards

Scope of this branch (`feature/AXF-104-coverage`): the Sprint 4 PR gate failed on Apex coverage with
`AXF_CLS_ObligationAdjustmentHandler` at 69.048% and `AXF_CLS_SettlementDecisionHandler` at 69.444%.
Both are trigger handlers whose shape guards only run while `ALT_CLS_ObligationService.isWriting()` is
true. The service builds valid records, so every guard was unreachable from the existing tests, which
only exercised the `!allowed` branch and the `beforeUpdate`/`beforeDelete` paths.

## Production change (one annotation, plus the two comment lines that justify it)

`ALT_CLS_ObligationService.writing` is annotated `@TestVisible`. It remains a private static whose value
is `false` outside an authorised write, and the annotation changes neither its visibility nor its value
at runtime: the service still owns the only two transitions (`writing = true` inside a command and
`writing = false` in the matching `finally`). One annotation is the minimum diff that makes the guard
state reachable from a test, and it follows the seam the class already exposes for
`authorizedAccounts` / `authorizedAccountsUser`.

## Tests added (`ALT_CLS_ObligationServiceTest`)

- `obligationAdjustmentShapeGuardsRejectAndAdmit` — every guard of `handleBeforeInsert` is driven with
  the input it exists for (missing and zero signed amount; missing occurrence; missing decision; blank
  currency, kind and reason; a COMPENSATION without its original; an ordinary adjustment pointing an
  original), asserting the single expected error message, plus the admitted shapes (valid adjustment,
  and a compensation carrying the opposite value of the adjustment it neutralises), the negative control
  of the capability, and a mixed batch where an invalid record does not contaminate a valid one.
- `settlementDecisionShapeGuardsRejectAndAdmit` — the same for the decision guards (decision key,
  occurrence, operation, classification, economic date, actor, committed instant, mode only on
  APPLY/CLASSIFY, components only on EXPLAINED, mandatory components, non-negative components, the
  equation against the effective obligation, coverage hash and coverage count), plus the shapes that
  mirror production: full EXPLAINED after a cash application, CLASSIFY, UNCLASSIFIED without components,
  REVERSE, AMEND_OBLIGATION, explicit zeros against absent components, the capability-off control and a
  mixed batch.
- `evidenceUpdateAdmitsResultCompletionAndUnchangedValues` — the receipt admits only the completion of
  its own result; a value resent unchanged is not a rewrite, while a component introduced after
  settlement is.

The handlers are called directly inside the authorised state, so no evidence row is written and the
capability is reset in a `finally`.

The single uncovered decision line is the `newValue == null && oldValue == null` return of the private
`isChanged` comparator. An update that assigns null to a field does not populate that field, so the
comparator is never reached with null on both sides; the acceptance run keeps that line as the only
uncovered one.

## Known gap in the original AXF-104 delivery (not addressed here)

`AXF_CLS_SettlementDecisionHandler.handleBeforeUpdate` never reads the write capability: the completion
field `AXF_SDC_TAL_ResultJson__c` is exempt from the immutability comparison for every caller, and
`replay()` deserializes exactly that field to return the stored result. Closing that gap changes the
AXF-104 production contract, so it is left to the owning issue; the guard suite now asserts the exemption
explicitly (`evidenceUpdateAdmitsResultCompletionAndUnchangedValues`) so the behavior cannot change
silently.
