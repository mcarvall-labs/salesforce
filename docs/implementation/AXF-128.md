# AXF-128 — Neutralização de contrapartidas no consolidado, replay e reversão

- **Jira:** https://axon-personal-finances.atlassian.net/browse/AXF-128 (parent AXF-1; split from AXF-5)
- **Branch:** `feature/AXF-128-neutralization` (base `origin/sprint/sprint-4` @ `91bf6db`).
- **Siblings already delivered and extended, not rebuilt:** AXF-126 (`propose`/`confirm`/`discard`,
  guard, integrity reads, controller) and AXF-127 (derived singular projection).

> Two rules only: (1) the counter-entries derived from a confirmed economic allocation are netted
> atomically **only** when the calculation receives every participant as an authorized holder — the
> consolidated view — while any narrower view keeps its own contribution; (2) the allocation's
> reversal creates compensating records and never edits the confirmation, with an equivalent replay
> returning the durable result and a divergent payload conflicting. No new object, field, permission
> set, Custom Label or metadata container.

## AC-1 → implementation

**Derived internal counter-entries.** A confirmed allocation of a fact derives one counter-entry per
parcel, between the fact's holder and the allocated person/company. `FR-50` defines them by their
function: they "reconcile the individual views" of the two sides and are "neutralized only in the
consolidation".

**Only in the consolidated view, atomically.** Before counting, the calculation asks whether _every_
participant of that fact's allocation is present as a fully authorized holder (`fullScope`, i.e. the
same `UserRecordAccess.HasAllAccess` test that AXF-122 already applies to a holder's coverage). The
decision is taken once per fact, so a fact is never netted by halves:

- **Complete perimeter** → the counter-entries are neutralized: the fact contributes once, through its
  economic attribution (`ALLOCATION` parcels), and the material fact is not counted again. 300 split
  70/30 contributes 210 + 90 = 300, never 600.
- **Incomplete perimeter** (any participant outside the scope or with unverified coverage) → nothing is
  netted. The fact keeps its contribution where it materially is, on its holder (`HOLDER`), and every
  authorized participant **other than the holder** still contributes its own parcel. The holder's own
  parcel is skipped precisely because it is already inside that material contribution. **Both legs of
  that pending counter-entry therefore remain in the result**, so a total summed across such individual
  views exceeds the material sum (600 against 500 in the AXF-122 fixture) and must not be read as a
  consolidated total — see the PO caveat under "Judgement calls and residuals".

**Individual views preserve their redacted contribution.** With the reversal of the old unconditional
behaviour, a holder whose fact was allocated away no longer loses its own fact: the holder's own view
shows its contribution, and no participant outside the scope is named or counted — the existing
`ALLOCATED_OUTSIDE_SCOPE` / `ALLOCATED_TO_UNVERIFIED_HOLDER` exclusions and `DEGRADED` confidence are
reused unchanged, so a pending counter-entry is never presented as if it had been netted.

## AC-2 → implementation

**Reversal creates compensating records.** `reverse(setId, expectedVersion, operationKey)` writes, in
one savepointed transaction:

1. a **compensating set** — same fact identity, next revision (`max(revision of that fact, in any
state) + 1`, so an intervening draft or a discarded one is respected), `SetKey = key(identity,
revision)`, created `DRAFT` and then `CONFIRMED` so the guard's own transition rules apply, with a
   **single 100% parcel for the fact's own holder**, conserving magnitude and original currency. That
   is the parity rule confirmation itself applies (`confirm()`), applied mechanically — not a new rule;
2. its `AXF_EAS_TXT_OperationKey__c` = the **G6 identity of this effect**,
   `IdentityFraming.key([OP_REVERSE, operationKey])` — framed under its own operationId so it can never
   be confused with a raw `propose` key stored in the same field;
3. the end of the confirmation — `REVERSED` state, version + 1, and, in the _same_ DML, the release of
   the single active token (unique field, so the compensation can take it) and the clearing of the
   derived singular projection (AXF-127: it does not outlive the set's authority).

Once done, the compensating set is the only `CONFIRMED` set of that fact and holds the active token:
the fact keeps exactly one attribution authority, now back at its holder.

**The confirmation is never edited.** Every identity field of the reversed set (`FactIdentity`,
`SetKey`, anchors, holder, magnitude, currency, revision), both operation keys, and **every parcel byte
for byte** (`Id`, account, percent, magnitude, currency, redaction policy, `AllocationKey`) are captured
before and asserted identical after. Only state, optimistic version, active token and projection move.

**Replay and conflict.** An equivalent replay — same framed key, same expected version — returns the
durable compensation read back from the database and appends nothing (the set count of the fact stays
at two). The compensation is identified by the **ratified operation key plus the fact identity**, never
by an inferred revision: `nextRevision()` takes the highest revision of the fact in _any_ state, so an
intervening `DRAFT` (or a discarded one) pushes the compensation past `reversed.Revision + 1` and a
revision-based rule would conflict the same command against its own durable effect. A divergent payload
never produces a second compensation: a different version under the same key conflicts, a stale version
on a live confirmation conflicts before anything is written, and a key already spent — on another fact,
on another confirmation, or by an earlier reversal — conflicts **before the write** as well, because
`AXF_EAS_TXT_OperationKey__c` is **not unique** and the same framed key must not be able to append a
second compensating set for a different target. The key lookup that answers a replay applies the same
discipline as the AXF-25 sibling (which filters by its original-allocation lookup): it filters by the
fact identity, has **no blind `LIMIT 1`**, and picks the highest-revision `CONFIRMED` row of _this_ fact,
so a foreign row that reuses the key can never answer for it. A `DRAFT` is never reversed
(`NOT_CONFIRMED`), and capability is checked before any set is read (`FORBIDDEN`).

The reversal gate conserves the fact **including its identity**: magnitude, currency, holder _and_
`FactIdentity` are compared, so a fact whose source key changed after the confirmation cannot be
compensated; and the compensating parcel goes back to the fact's own holder, so that person/company
must still be an authorized holder. Either failure is `REVERSAL_REJECTED` and nothing is written.

**The guard releases on the transition, not on the destination state.** `ALT_CLS_EconomicAllocationGuard`
grants the two transition-bookkeeping fields (`ActiveToken`, `AttributedAccount`) only when the state
really **changes** from `CONFIRMED` into an ending state, so re-asserting an already-ended state
(`REVERSED → REVERSED`, `SUPERSEDED → SUPERSEDED`) releases nothing and neither field becomes writable
while the set stays `CONFIRMED`. On that transition the active token may only be **released**: if it is
written at all it must be written as null, never moved to another value — the field is unique, so a
value planted there would block another fact's `propose` for good with `ACTIVE_SET_EXISTS`. And the
handover must already exist: a live set of the same fact at a **higher revision** must be present in the
same transaction, so a confirmation cannot be ended without its compensating set.

## Judgement calls and residuals

- **Two AXF-122 assertions were corrected, not weakened.** `confirmedAllocationSharesFollowAttribution`
  and `allocationSharesAreValidatedRoundedAndUnverifiedHoldersDistinguished` encoded the _unconditional_
  neutralisation (the holder's material fact dropped whenever a confirmed allocation existed, and a
  fact netted by halves when one participant was missing). Under the ratified rule the same fixtures now
  assert the corrected totals (400 → 600 and 333.35333334 → 400.02333334) **plus** the newly preserved
  holder contribution; in the first fixture the `Assert.isNull` on the holder's contribution was
  replaced by assertions on the contribution that now exists (`HOLDER`, 200) — that replacement _is_
  the correction, and the arithmetic of both new totals was confirmed by an independent acceptance
  audit. No assertion was deleted or skipped and no test was disabled. Neither file is fully green on
  `AXON_DEV`: the same run reports the two pre-existing reds listed under Validation. "Green" is
  therefore claimed only for what this pass touches — every AXF-126/AXF-127 test, the corrected AXF-122
  assertions, and the tests this pass adds.
- **PO caveat, stated explicitly (raised by the audit).** Under a **non-consolidated** perimeter nothing
  is netted, so **both legs of the pending counter-entry remain**: the holder keeps the material fact
  _and_ the authorized participant keeps its parcel. A total summed across such individual views is
  therefore **not a consolidated total** and now exceeds the material sum — in the AXF-122 fixture
  `confirmedAllocationSharesFollowAttribution` it sums **600** against a material **500** (300 + 200
  facts, with 200 + 100 double-counted across the two views of the pending pair). That is the declared
  rule of AXF-128, not a defect: the pair reconciles the two individual views and is neutralized only
  when _every_ participant is an authorized holder, and in that narrower perimeter the result is
  reported `DEGRADED` with `ALLOCATED_OUTSIDE_SCOPE` precisely so it is never presented as if it had
  been netted. Whoever sums cross-view totals must keep the per-view perimeter, which is what the
  confidence and the exclusion reasons exist to signal.
- **Re-allocation after a reversal is a different operation.** The compensating set holds the active
  token, so `propose` refuses a new revision (`ACTIVE_SET_EXISTS`) exactly as it does for any confirmed
  set; re-allocating a fact is the sibling `economicallocation.set.revise.v1` (supersession), which no
  AXF-128 acceptance criterion requires and which is therefore **not implemented** here.
- **PENDENCY — `SUPERSEDED` has no writer and no test.** The guard still allows the
  `CONFIRMED → SUPERSEDED` transition (the transition table is unchanged and the ending rules above
  apply to it), but nothing in this delivery writes `SUPERSEDED`, so that path is **unexercised**: both
  `reverse.v1` and every test move a set to `REVERSED` only, and supersession is the sibling `revise.v1`
  that no AC here requires. If `revise.v1` arrives, the ending rules it will have to satisfy are: real
  state change, token written only as null, and a live successor at a higher revision.
- **PENDENCY — `reverse.v1` has no user-facing entry point.** `AXF_CLS_CTRL_EconomicAllocation` exposes
  `getContext`/`propose`/`confirm`/`discard` only, while the AXF-25 sibling reversal service ships a
  controller of its own. `reverse.v1` is therefore reachable from Apex (and from the tests) but not from
  the UI. Whether AC-2 requires a user-reachable operation is a product decision, not something this
  pass may settle: the AC is worded about the effect (equivalent replay returns the durable result, a
  divergent payload conflicts, a reversal never edits the confirmation), and no controller was added
  here — adding one would also need an LWC surface and its own Jest coverage.
- **RESIDUAL — no explicit link between the compensation and the confirmation it reverses.** The AXF-25
  sibling stores an original-allocation lookup plus a payload fingerprint on its compensation. The
  ratified §5 field list of `AXF_EAS` defines no "reverses" lookup and no reversal reason, and changing
  §5 is an "Ask First" contract amendment, so no field was invented: the compensation is identified by
  its fact identity plus the framed operation key, and the reversed confirmation is identified by the
  fact identity plus the fact that it is the `REVERSED` set. A future amendment that ratifies such a
  field would make this link explicit and cheap to assert.
- **RESIDUAL — an omitted active token cannot be judged in a before trigger.** A before-update trigger
  sees neither the stored value nor the resulting one for a field that is not written, and an explicit
  `null` is indistinguishable from an omitted field, so the guard can only reject a token that is
  _written_ with a value. A caller inside the service write window could therefore still end a
  confirmation while leaving its own token behind — blocking that same fact's later `propose`
  (`ACTIVE_SET_EXISTS`), never another fact's. Closing it would need an after-update check on the set,
  which this pass does not add.
- **The successor lookup reads the fact and the revision from the database, not from the payload.**
  The handover requirement is one query for the whole DML: the ending sets are read back by Id for their
  stored revision, the live sets of the same fact anchors (`DRAFT`/`CONFIRMED`) supply the successor
  candidates, and the ending sets are excluded from their own candidates. Neither the fact identity nor
  the revision therefore has to be present in the update payload, which a partial write would not carry.
- **No reason/note field was added.** The ratified §5 field list has no reversal reason or "reverses"
  lookup, and the spec's "Ask First" list makes changing §5 a contract amendment. The compensating set
  is linked to what it compensates by its fact identity plus the next revision — the relation the guard
  itself already names ("reverse with a compensating set").
- **`AXF_EAS_TXT_OperationKey__c` widened in meaning.** Its description now reads
  `propose/confirm/reverse`, because that field is documented as "the idempotency key of the last
  applied operation" and the reversal stores its framed key there. The alternative — a dedicated field —
  would have changed the ratified §5 contract.
- **The `personHoldersAreAuthorizedAndNonAxonAccountsAreNotHolders` red is pre-existing.** It asserts
  `result.holders.size() == 1` for a scope holding one Axon person plus `new Account(Name = 'Conta
Comum')` created **without** an explicit record type. `AXON_DEV` has only two Account record types
  (`AXF_Person`, `AXF_Business`, queried in this session), so the default one applies, the account
  becomes a valid holder and the count is 2. Reproduced identically with the pristine
  `origin/sprint/sprint-4` classes deployed and run before this pass's changes (see Validation).
