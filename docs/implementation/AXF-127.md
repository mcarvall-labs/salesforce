# AXF-127 — Derived singular attribution projection vs. apportionment

- **Jira:** https://axon-personal-finances.atlassian.net/browse/AXF-127 (parent AXF-1; split from AXF-5)
- **Branch:** `feature/AXF-127-single-attribution` (base `origin/sprint/sprint-4` @ `39020a6`).
- **Sibling already delivered:** AXF-126 — propose/confirm economic allocation (100% exact). This
  story **extends** it; it does not recalculate, propose or create any allocation.

> One rule only: the derived singular projection is written at confirmation, mirrors a sole
> 100% person/company, and stays empty under apportionment. No new object, field, permission set,
> Custom Label or metadata of any kind.

---

## What "G1" is

The AC reads "…the derived single-attribution projection may reflect that person/company, **per
G1**". G1 is **not** a rule about the projection, and it is not a permission to populate it:

> **G1 = Gate 1 — physical data model** (`readiness.md:50,59`; `ARCHITECTURE-SPINE.md:63`,
> AD-4 at `:106-107`), **closed 30/08/2026**. Decision: the root of titularity is `Account` —
> **Person Account** for a person and **Business Account** for a company. `Household` and the
> custom `FinancialEntity` are **not** created, with no renamed substitute (D-51, D-77, D-78);
> an isolated `Contact` is not a holder either.

So G1 constrains the **shape of the subject**, not the timing or the authority of the projection:
the singular subject must be an `Account` of record type `AXF_Person` or `AXF_Business`. It
therefore does not add a check here — it _confirms_ that deriving the projection from an
allocation share is correct by construction, because `authorizedHolders()` already rejects any
share whose account is not one of those two record types. Had the projection been modelled on
`Contact`, `User` or a custom `FinancialEntity`, G1 would have made it invalid; on `Account` it is
G1-conformant with no extra code.

Everywhere below, "G1" is used only for that form constraint. It is **not** the source of the
rule that the value is written at confirmation, of the rule that apportionment leaves it empty, or
of the rule that it is never an authority: those come from the ratified contract cited next. The
code comments that used to attribute them to G1 were corrected with this pass
(`ALT_CLS_EconomicAllocationService`, class header, `confirm` and `attributedAccount`).

**Timing and authority** come from the ratified AXF-5 lineage contract instead:
`AXF-5-ECONOMIC-ALLOCATION-RECONCILIATION.md` §5 (`AXF_EAS_LKP_AttributedAccount__c`, ratified
13/09/2026) and the AXF-5 spec Boundaries — _"preenchida apenas quando o set `CONFIRMED` tem
exatamente uma parcela de 100%, limpa em rateio, e **nunca** autoridade de acesso nem entrada de
cálculo"_.

## AC → implementation

- **Given an integral allocation to a single person/company, when the projection is updated, then
  the derived projection may reflect that person/company, per G1.** Exactly one allocation whose
  percent is 100 ⇒ `attributedAccount()` returns that allocation's `AXF_EA_LKP_Account__c`. The
  account is a Person or Business `Account` because `authorizedHolders()` gated it — that is the
  whole of G1's contribution here. "When the projection is updated" is the `DRAFT → CONFIRMED`
  transition, and that timing is the contract's, not G1's.
- **Under apportionment the singular projection stays empty and never becomes an authority.**
  `attributedAccount()` returns `null` unless the set composes to exactly one 100% parcel, so two
  or more shares always derive `null` — no primary, first or largest participant is ever picked.
  This clause is taken from the ratified contract ("limpa em rateio, e **nunca** autoridade de
  acesso nem entrada de cálculo"), not from G1. The value is written but read nowhere: it is not
  consulted by `authorizedHolders()`, by the sharing model, by `shareMagnitudes()` or by any DTO,
  so it grants no access and enters no calculation. After confirmation the guard freezes it
  (`CONFIRMED_MUTABLE` does not include it), so it cannot be flipped into an authority later; and a
  set that loses its authority stops carrying it — see "G1 — the projection does not outlive the
  set's authority" below.

## Why the projection is written at confirmation

The rule that the value belongs to the confirmed state is the ratified contract's (AXF-5 §5: it is
filled only while the set is `CONFIRMED` with exactly one 100% parcel). The guard only decides
**where** that write can happen: the single-item guard (`ALT_CLS_EconomicAllocationGuard.sets`)
forbids changing any `__c` field of a set that is already `CONFIRMED`, except state and optimistic
version. A projection written after confirmation would therefore be rejected, and a projection
written at `propose` time would publish a singular attribution for a set that is still a `DRAFT`
and may never be confirmed. Writing it in the `DRAFT → CONFIRMED` update is the only point that is
both atomic with the confirmation and permitted by the guard.

## Clearing a previously set value

The assignment is deliberately **unconditional**, so an apportioned confirmation writes `null`
rather than leaving a stale value behind. The state "a set already carrying a singular projection
is then confirmed as apportionment" is **not reachable through the service**: revision/supersession
is the sibling story AXF-128 and `propose()` currently refuses a second revision while an active
set exists (`ACTIVE_SET_EXISTS`), re-confirmation of a confirmed set is refused (`NOT_DRAFT`), and
direct DML on a confirmed set is refused by the guard. `apportionedConfirmationClearsAPreexistingProjection`
therefore seeds its precondition through the `DRAFT` content window the guard deliberately allows,
and proves the totality of the assignment rather than a reachable service path.

## G1 — the projection does not outlive the set's authority

The projection is a derived statement about **who holds the authority for that fact**. It is
readable (FLS `AXF_PS_GestorFinanceiro`, `editable=true`) and visible to reports and list views, so
a set that has lost its authority must not keep a singular attribution that no longer corresponds
to any confirmed allocation. `discard()` therefore clears `AXF_EAS_LKP_AttributedAccount__c` in the
same DML that moves the set `DRAFT → DISCARDED` — the same assignment point `confirm()` uses when
the authority begins, which is what "consistent with the confirmation path" means here. Clearing
only, no other discard behaviour changed.

**Residual, deliberately not implemented here:** `CONFIRMED → SUPERSEDED | REVERSED` are transitions
performed by AXF-128, and **no writer for them exists on this branch** (the guard permits them; the
service has no method for them). Because confirmed content is frozen except state and version, the
clearing for those two transitions has to ride in the same update that performs the transition —
exactly as `discard()` and `confirm()` do it here. Until AXF-128 adds those methods, a superseded or
reversed set keeps whatever projection it had confirmed with. Transition semantics are AXF-128's and
were not implemented in this pass.

## Out of scope

Revision/supersession and reallocation (AXF-128), compensating neutralisation/reversal (AXF-128),
third-party payment (AXF-129), surfacing the projection in any UI, and any change to percentages,
rounding, identity or recognition.

## Declared pendencies (not implemented in this pass)

- **No backfill for sets already `CONFIRMED` under AXF-126.** The projection is written only on the
  `DRAFT → CONFIRMED` transition and the guard freezes the field afterwards, so a set confirmed
  before this change keeps a **permanently null** projection that cannot be repaired through the
  service: `confirm()` refuses a non-`DRAFT` set, direct DML on a confirmed set is refused by the
  guard, and no other entry point touches the field. Historical integral allocations therefore show
  no singular attribution. This is an **open gap needing a decision** (backfill script versus
  accepted hole); it is also recorded in the deferred-work ledger.
- **The G1 form guarantee has no green test.** The only test asserting that a non-Axon account is
  rejected is `invalidSharesAreRejectedAtomicallyWithoutPartialPersistence`, which is already red in
  `AXON_DEV` for an org-data reason (below) and belongs to AXF-126 — it was **not modified**. So the
  guarantee that the projected subject is always an `AXF_Person`/`AXF_Business` `Account` is
  enforced by `authorizedHolders()` but not proven by a passing test on this branch. Recorded as a
  gap, not fixed.
- **`CONFIRMED → SUPERSEDED | REVERSED` clearing** belongs to AXF-128 (no writer for those
  transitions exists here) — see "G1 — the projection does not outlive the set's authority".

### Known pre-existing failure in this class

`invalidSharesAreRejectedAtomicallyWithoutPartialPersistence` (AXF-126 — the `UNAUTHORIZED_ACCOUNT:`
assertion) fails in `AXON_DEV` **independently of this change**: it was reproduced identically with
the pristine `origin/sprint/sprint-4` class deployed and verified in the org, and it failed the same
way before and after this pass. Cause is org data, not code: an `Account` created without an
explicit record type receives `AXF_Business` in this org (measured in a test running as the same
`Standard User` test user: `[SELECT RecordType.DeveloperName FROM Account]` → `AXF_Business`), so
`new Account(Name = 'Conta comum sem tipo Axon')` silently becomes a valid holder and no
`UNAUTHORIZED_ACCOUNT` reason is produced. A non-Axon account would need an explicit record type
(e.g. `Master`, which is active and available). The test is AXF-126's and was left untouched.
