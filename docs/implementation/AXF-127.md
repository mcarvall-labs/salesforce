# AXF-127 — Derived singular attribution projection vs. apportionment

- **Jira:** https://axon-personal-finances.atlassian.net/browse/AXF-127 (parent AXF-1; split from AXF-5)
- **Branch:** `feature/AXF-127-single-attribution` (base `origin/sprint/sprint-4` @ `39020a6`).
- **Sibling already delivered:** AXF-126 — propose/confirm economic allocation (100% exact). This
  story **extends** it; it does not recalculate, propose or create any allocation.

> One rule only: the derived singular projection is written at confirmation, mirrors a sole
> 100% person/company, and stays empty under apportionment. No new object, field, permission set,
> Custom Label or metadata of any kind.

---

## What "G1" is

The AC reads "…the derived single-attribution projection may reflect that person/company, **per
G1**". G1 is **not** a rule about the projection, and it is not a permission to populate it:

> **G1 = Gate 1 — physical data model** (`readiness.md:50,59`; `ARCHITECTURE-SPINE.md:63`,
> AD-4 at `:106-107`), **closed 30/08/2026**. Decision: the root of titularity is `Account` —
> **Person Account** for a person and **Business Account** for a company. `Household` and the
> custom `FinancialEntity` are **not** created, with no renamed substitute (D-51, D-77, D-78);
> an isolated `Contact` is not a holder either.

So G1 constrains the **shape of the subject**, not the timing or the authority of the projection:
the singular subject must be an `Account` of record type `AXF_Person` or `AXF_Business`. It
therefore does not add a check here — it _confirms_ that deriving the projection from an
allocation share is correct by construction, because `authorizedHolders()` already rejects any
share whose account is not one of those two record types. Had the projection been modelled on
`Contact`, `User` or a custom `FinancialEntity`, G1 would have made it invalid; on `Account` it is
G1-conformant with no extra code.

**Timing and authority** come from the ratified AXF-5 lineage contract instead:
`AXF-5-ECONOMIC-ALLOCATION-RECONCILIATION.md` §5 (`AXF_EAS_LKP_AttributedAccount__c`, ratified
13/09/2026) and the AXF-5 spec Boundaries — _"preenchida apenas quando o set `CONFIRMED` tem
exatamente uma parcela de 100%, limpa em rateio, e **nunca** autoridade de acesso nem entrada de
cálculo"_.

## AC → implementation

- **Given an integral allocation to a single person/company, when the projection is updated, then
  the derived projection may reflect that person/company, per G1.** Exactly one allocation whose
  percent is 100 ⇒ `attributedAccount()` returns that allocation's `AXF_EA_LKP_Account__c`. The
  account is a Person or Business `Account` because `authorizedHolders()` gated it (G1).
- **Under apportionment the singular projection stays empty and never becomes an authority.**
  `attributedAccount()` returns `null` unless the set composes to exactly one 100% parcel, so two
  or more shares always derive `null` — no primary, first or largest participant is ever picked.
  The value is written but read nowhere: it is not consulted by `authorizedHolders()`, by the
  sharing model, by `shareMagnitudes()` or by any DTO, so it grants no access and enters no
  calculation. After confirmation the guard freezes it (`CONFIRMED_MUTABLE` does not include it),
  so it cannot be flipped into an authority later.

## Why the projection is written at confirmation

The single-item guard (`ALT_CLS_EconomicAllocationGuard.sets`) forbids changing any `__c` field of
a set that is already `CONFIRMED`, except state and optimistic version. A projection written after
confirmation would therefore be rejected, and a projection written at `propose` time would publish
a singular attribution for a set that is still a `DRAFT` and may never be confirmed. Writing it in
the `DRAFT → CONFIRMED` update is the only point that is both atomic with the confirmation and
permitted by the guard.

## Clearing a previously set value

The assignment is deliberately **unconditional**, so an apportioned confirmation writes `null`
rather than leaving a stale value behind. The state "a set already carrying a singular projection
is then confirmed as apportionment" is **not reachable through the service**: revision/supersession
is the sibling story AXF-128 and `propose()` currently refuses a second revision while an active
set exists (`ACTIVE_SET_EXISTS`), re-confirmation of a confirmed set is refused (`NOT_DRAFT`), and
direct DML on a confirmed set is refused by the guard. `apportionedConfirmationClearsAPreexistingProjection`
therefore seeds its precondition through the `DRAFT` content window the guard deliberately allows,
and proves the totality of the assignment rather than a reachable service path.

## Out of scope

Revision/supersession and reallocation (AXF-128), compensating neutralisation/reversal (AXF-128),
third-party payment (AXF-129), surfacing the projection in any UI, and any change to percentages,
rounding, identity or recognition.

### Known pre-existing failure in this class

`invalidSharesAreRejectedAtomicallyWithoutPartialPersistence` (AXF-126, line 415 — the
`UNAUTHORIZED_ACCOUNT:` assertion) fails in `AXON_DEV` **independently of this change**: it was
reproduced identically with the pristine `origin/sprint/sprint-4` class deployed and verified in
the org. Cause is org data, not code: `AXF_Person` is the **default** Account record type in this
org, so `new Account(Name = 'Conta comum sem tipo Axon')` silently receives that record type and
the account _is_ a valid holder, so no `UNAUTHORIZED_ACCOUNT` reason is produced. A non-Axon
account would need an explicit record type (e.g. `Master`, which is active and available). The
test is AXF-126's and was left untouched.
